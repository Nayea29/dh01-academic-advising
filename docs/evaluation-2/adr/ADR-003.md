# ADR-003 — Controlled Case Lifecycle and Transactional Consistency

**Proyecto:** DH-01 — Academic Advising Case Management System

**Estado:** Propuesta seleccionada, sujeta a validación de reglas operacionales

**Architecture Drivers:** AD-01, AD-04

**Escenarios relacionados:** QS-02, QS-03

## 1. Contexto

La gestión de casos académicos comprende diferentes etapas desde la creación de una solicitud hasta su resolución.

Las operaciones deben respetar reglas como la clasificación antes de la asignación, la conservación del historial de reasignaciones y la imposibilidad de resolver casos con actividades obligatorias pendientes.

Es necesario impedir transiciones no válidas y evitar inconsistencias cuando se ejecuten operaciones concurrentes.

## 2. Alternativas consideradas

### Alternativa A — Controlar estados desde la interfaz

Consiste en habilitar u ocultar acciones en la aplicación web según el estado actual del caso.

Esta solución puede mejorar la experiencia del usuario, pero no protege por sí sola las operaciones del backend.

Un usuario podría enviar solicitudes directamente a la API o trabajar con información desactualizada.

### Alternativa B — Validaciones independientes en cada endpoint

Cada endpoint verifica sus condiciones antes de ejecutar una operación.

Aunque permite aplicar reglas en el servidor, existe el riesgo de duplicar lógica y generar comportamientos diferentes entre operaciones relacionadas.

### Alternativa C — Modelo centralizado de transiciones y reglas de dominio

Las transiciones se controlan mediante operaciones de aplicación que verifican el estado actual, el actor autorizado y las condiciones de negocio.

Las modificaciones relacionadas se realizan mediante transacciones consistentes.

## 3. Decisión

Se selecciona la alternativa C.

El sistema utilizará un modelo explícito del ciclo de vida con los siguientes estados principales propuestos:

- NEW.
- UNDER_TRIAGE.
- ASSIGNED.
- IN_PROGRESS.
- WAITING_FOR_INFORMATION.
- FOLLOW_UP.
- RESOLVED.

La lista definitiva y las transiciones permitidas requieren validación institucional.

El backend será responsable de verificar las condiciones de cada transición.

Las operaciones que requieran modificar varios registros relacionados se ejecutarán dentro de una transacción.

En particular, la resolución de un caso y los cambios sobre follow-ups deberán coordinarse mediante una estrategia de concurrencia que impida confirmar estados contradictorios.

## 4. Reglas de integridad principales

**Regla 1 — Clasificación antes de asignación**

Una asignación definitiva requiere que el caso haya completado el proceso de clasificación correspondiente.

**Regla 2 — Resolución sin pendientes**

Un caso no puede pasar a RESOLVED mientras existan actividades obligatorias de asesoría pendientes.

**Regla 3 — Historial conservado**

Una reasignación no elimina los registros históricos de responsabilidad.

**Regla 4 — Transiciones autorizadas**

Cada operación debe comprobar el permiso del usuario y la validez de la transición.

**Regla 5 — Consistencia concurrente**

Una operación concurrente de creación de follow-up y resolución del caso no debe generar simultáneamente un caso resuelto con una actividad obligatoria pendiente.

## 5. Consecuencias

**Positivas:**

- Reglas de negocio centralizadas.
- Mayor consistencia del ciclo de vida.
- Comportamiento verificable.
- Reducción de transiciones no autorizadas.
- Mejor trazabilidad de acciones.

**Limitaciones:**

- Se necesita definir cuidadosamente el modelo de estados.
- Las operaciones concurrentes requieren mecanismos adicionales de control.
- Los cambios en las reglas de transición deberán acompañarse de pruebas de regresión.

## 6. Verificación

Se ejecutarán pruebas que cubran:

- Asignaciones sin clasificación.
- Transiciones no válidas.
- Intentos de resolución con follow-ups pendientes.
- Resolución después de completar las acciones requeridas.
- Operaciones concurrentes de seguimiento y cierre.
- Conservación de la información después de reasignaciones.

**Pruebas relacionadas:** T-LIFE-01, T-LIFE-02 y T-AUD-01.

## 7. Condiciones para reconsiderar la decisión

La estrategia podrá revisarse si las políticas institucionales introducen flujos considerablemente más complejos, con múltiples aprobaciones, estados paralelos o procesos de larga duración que justifiquen un motor de workflows.
