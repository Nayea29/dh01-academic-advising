# ADR-003 — Controlled Case Lifecycle and Transactional Consistency

## 1. Contexto

La gestión de casos académicos comprende diferentes etapas, desde la creación de una solicitud hasta su resolución.

Durante este proceso, el sistema debe respetar reglas como la clasificación previa a la asignación, la existencia de un responsable vigente, la conservación del historial de reasignaciones y la imposibilidad de resolver casos con actividades pendientes.

También es necesario impedir transiciones no válidas y evitar inconsistencias cuando varios usuarios ejecuten operaciones sobre un mismo caso.

Por ejemplo, una resolución y la creación de una nueva actividad de seguimiento no pueden confirmarse de forma que el caso termine resuelto con una actividad pendiente.

Estas necesidades requieren un mecanismo centralizado para controlar las transiciones y coordinar los cambios relacionados.

## 2. Alternativas consideradas

### Alternativa A — Controlar estados desde la interfaz

Consiste en habilitar u ocultar acciones en la aplicación web según el estado actual del caso.

**Ventajas:**
- Implementación inicial relativamente sencilla.
- Permite orientar al usuario hacia las acciones disponibles.
- Facilita mostrar el estado del caso y sus operaciones permitidas.

**Desventajas:**
- No protege por sí sola las operaciones del backend.
- Un usuario podría enviar solicitudes directamente a la API.
- La interfaz puede trabajar con información desactualizada.
- No garantiza consistencia ante operaciones concurrentes.

Esta alternativa puede complementar la experiencia de usuario, pero no debe considerarse el mecanismo principal de integridad.

### Alternativa B — Validaciones independientes en cada endpoint

Cada endpoint verifica sus condiciones antes de ejecutar una operación.

**Ventajas:**
- Las validaciones se ejecutan desde el backend.
- Permite implementar las reglas necesarias para cada operación.

**Desventajas:**
- Riesgo de duplicar lógica entre endpoints.
- Posibilidad de generar comportamientos distintos para reglas equivalentes.
- Mayor dificultad para mantener políticas y transiciones.
- Las validaciones aisladas no resuelven automáticamente los conflictos concurrentes.

### Alternativa C — Modelo centralizado de transiciones y reglas de dominio

Las transiciones se controlan mediante operaciones de aplicación que verifican el estado actual, el actor autorizado y las condiciones de negocio.

Los cambios relacionados se coordinan mediante transacciones consistentes.

**Ventajas:**
- Reglas de negocio centralizadas y verificables.
- Aplicación uniforme de las condiciones de transición.
- Mejor control de operaciones concurrentes.
- Facilidad para relacionar cada operación con su auditoría.
- Mayor claridad para modificar políticas futuras.

**Desventajas:**
- Requiere diseñar cuidadosamente las transiciones y sus condiciones.
- Necesita mecanismos explícitos de concurrencia y persistencia.
- Los cambios de reglas pueden afectar varios casos de prueba y contratos.

## 3. Decisión

Se selecciona la **alternativa C: modelo centralizado de transiciones y reglas de dominio**.

El sistema utilizará un ciclo de vida explícito con los siguientes siete estados propuestos:

- `NEW`
- `UNDER_TRIAGE`
- `ASSIGNED`
- `IN_PROGRESS`
- `WAITING_FOR_INFORMATION`
- `FOLLOW_UP`
- `RESOLVED`

La lista definitiva de estados y sus transiciones permitidas requiere validación institucional.

El backend C-API será responsable de ejecutar las operaciones del ciclo de vida, comprobar las autorizaciones y verificar las condiciones de negocio.

La creación del caso, el inicio del triage y la clasificación con asignación se realizarán como operaciones diferenciadas, evitando tratar la asignación como una consecuencia automática del registro inicial.

Para las operaciones críticas se utilizará PostgreSQL mediante una unidad de trabajo transaccional compartida.

Cuando varias operaciones puedan modificar condiciones relacionadas con un caso, deberán coordinarse mediante un protocolo común:

1. Iniciar la transacción.
2. Bloquear la fila correspondiente a `AdvisingCase` mediante `SELECT FOR UPDATE`.
3. Comprobar nuevamente la autorización, el estado y la versión esperada.
4. Validar las condiciones de negocio con información vigente.
5. Aplicar los cambios relacionados y registrar el evento obligatorio de auditoría.
6. Confirmar la transacción únicamente si todas las operaciones necesarias tienen éxito.

El campo `expectedVersion` permitirá detectar intentos de modificación basados en información desactualizada.

Los conflictos de estado o versión se comunicarán mediante las respuestas definidas en los contratos de API, incluyendo `409 Conflict` cuando corresponda.

La condición `OVERDUE` se manejará como un indicador derivado de las fechas y políticas de seguimiento, no como un octavo estado persistido.

## 4. Reglas de integridad principales

### Regla 1 — Clasificación antes de asignación

La asignación inicial requiere que el caso haya completado una clasificación válida.

El flujo separa la creación del caso, el inicio del triage y la clasificación con asignación. Un caso no deberá considerarse asignado únicamente por haber sido registrado.

### Regla 2 — Resolución sin pendientes

Un caso solo podrá pasar a `RESOLVED` cuando se cumplan todas las condiciones siguientes:

- El caso se encuentra en `IN_PROGRESS`.
- La operación la realiza el Academic Adviser actualmente asignado y autorizado.
- Existe al menos una `Recommendation` registrada.
- No existe ningún `InformationRequest` con estado `OPEN`.
- Todos los registros `FollowUp` del caso se encuentran en estado `COMPLETED`.
- La versión esperada coincide con la versión vigente del caso.

Estas condiciones se verificarán dentro de la transacción, después de obtener el bloqueo correspondiente.

La distinción futura entre actividades obligatorias y opcionales requeriría una modificación explícita de la política. En el flujo inicial, ningún FollowUp pendiente permite la resolución.

### Regla 3 — Historial conservado

Una reasignación no elimina ni sobrescribe las responsabilidades anteriores.

El cambio de responsable vigente y el evento correspondiente de auditoría deberán confirmarse dentro de la misma transacción.

### Regla 4 — Transiciones autorizadas

Cada operación deberá comprobar:

- Identidad y sesión válida del actor.
- Rol y alcance autorizado.
- Relación vigente con el caso.
- Estado actual del caso.
- Condiciones específicas de la transición.

Ocultar una acción en la interfaz no sustituye la autorización del backend.

### Regla 5 — Consistencia concurrente

Las operaciones que puedan afectar la resolución, los seguimientos o las solicitudes de información deberán compartir el mecanismo de coordinación transaccional del caso.

Por ejemplo, si la resolución y la creación de un nuevo FollowUp compiten sobre el mismo caso, únicamente podrá confirmarse una combinación de operaciones que respete las reglas del ciclo de vida.

La estrategia deberá impedir que un caso quede en `RESOLVED` con seguimientos pendientes o solicitudes de información abiertas.

### Regla 6 — Atomicidad de las operaciones

Los cambios de negocio y sus eventos obligatorios de auditoría deberán formar parte de una única transacción.

Si falla una modificación necesaria o la inserción del evento de auditoría, se revertirá toda la operación.

Esto evita conservar estados parciales o registrar como exitosa una operación que no se confirmó.

## 5. Consecuencias

**Positivas:**

- Reglas de negocio centralizadas.
- Mayor consistencia del ciclo de vida.
- Comportamiento verificable mediante pruebas.
- Prevención de transiciones inválidas.
- Control explícito de modificaciones concurrentes.
- Historial coherente con las operaciones confirmadas.
- Posibilidad de modificar políticas de manera controlada.

**Limitaciones y compromisos:**

- Es necesario definir cuidadosamente el modelo de estados y sus transiciones.
- Las operaciones concurrentes requieren bloqueos, control de versiones y transacciones correctamente implementadas.
- Las modificaciones de políticas deberán acompañarse de pruebas de regresión.
- Los mecanismos de bloqueo pueden introducir esperas o conflictos bajo carga concurrente.
- El diseño depende de la aplicación consistente del protocolo transaccional por los componentes involucrados.
- Las reglas operacionales propuestas siguen sujetas a aprobación institucional.

## 6. Verificación

La decisión se evaluará mediante las siguientes pruebas:

| Prueba | Objetivo |
|---|---|
| T-TRIAGE-01 | Comprobar que la asignación inicial exija una clasificación válida. |
| T-LIFE-01 | Verificar transiciones permitidas y rechazo de resoluciones que incumplan las condiciones de cierre. |
| T-LIFE-02 | Comprobar la consistencia cuando operaciones de seguimiento y resolución compiten sobre el mismo caso. |
| T-AUD-01 | Verificar que los cambios de estado y reasignaciones conserven el historial correspondiente. |
| T-TXN-01 | Comprobar que un fallo en una operación obligatoria revierta todos los cambios de la transacción. |
| T-API-01 | Verificar el tratamiento de versiones desactualizadas, conflictos y respuestas de API. |

La verificación incluirá casos positivos y negativos, especialmente:

- Intentar asignar un caso sin clasificación válida.
- Solicitar transiciones no permitidas.
- Resolver un caso sin Recommendation.
- Resolver un caso con InformationRequest OPEN.
- Resolver un caso con FollowUp pendiente.
- Resolver un caso después de completar todas las condiciones requeridas.
- Enviar operaciones con una versión desactualizada.
- Ejecutar operaciones concurrentes de seguimiento y resolución.
- Comprobar la conservación del historial después de una reasignación.
- Simular fallos transaccionales y verificar ausencia de cambios parciales.

Las pruebas de concurrencia y transacciones deberán utilizar PostgreSQL real en un entorno controlado, ya que una simulación en memoria no demuestra por sí sola las garantías del mecanismo seleccionado.

Los resultados se registrarán cuando se ejecuten las pruebas correspondientes.

## 7. Condiciones para reconsiderar la decisión

La estrategia podrá revisarse si las políticas institucionales introducen flujos considerablemente más complejos, por ejemplo:

- Múltiples aprobaciones independientes.
- Estados paralelos o procesos de atención simultáneos.
- Flujos de larga duración con reglas extensas de compensación.
- Escalamientos institucionales complejos.
- Reaperturas sujetas a nuevas condiciones y autorizaciones.
- Necesidad de un motor de workflows para administrar reglas que excedan el modelo actual.

La aparición de estos requisitos no implicará automáticamente adoptar otra arquitectura. Será necesario evaluar sus consecuencias, alternativas y costos antes de modificar la decisión.

Toda modificación deberá documentarse y relacionarse con los cambios correspondientes en requisitos, contratos, modelos y pruebas.
