# ADR-002 — Relational Database and Persistent Data Management

**Proyecto:** DH-01 — Academic Advising Case Management System

**Estado:** Propuesta seleccionada para el diseño

**Architecture Drivers:** AD-01, AD-03, AD-04

**Escenarios relacionados:** QS-02, QS-03, QS-07

## 1. Contexto

El sistema necesita conservar información estructurada relacionada con estudiantes, asesores, solicitudes, asignaciones, actividades de seguimiento y eventos históricos.

Estas entidades mantienen relaciones que deben respetarse durante las operaciones del sistema.

Por ejemplo, cada follow-up debe pertenecer a un caso válido y una reasignación debe actualizar el responsable sin perder la información histórica.

Asimismo, los cambios de estado y sus registros de auditoría deben mantenerse consistentes.

## 2. Alternativas consideradas

### Alternativa A — Base de datos documental

Una base de datos documental permite almacenar información flexible mediante documentos.

**Ventajas:**
- Flexibilidad de estructura.
- Adaptación a documentos con atributos variables.

**Desventajas:**
- Mayor responsabilidad de diseño para mantener relaciones e invariantes entre diferentes registros.
- El modelo de casos, usuarios, asignaciones y seguimientos requiere asociaciones explícitas.

Una base documental puede ofrecer transacciones, pero su flexibilidad no proporciona una ventaja determinante para las relaciones identificadas en DH-01.

### Alternativa B — Base de datos relacional

Una base de datos relacional permite representar entidades relacionadas mediante tablas, claves y restricciones de integridad.

**Ventajas:**
- Soporte para relaciones estructuradas.
- Restricciones de integridad referencial.
- Operaciones transaccionales.
- Consultas estructuradas para reportes.
- Herramientas maduras de administración.

**Desventajas:**
- Requiere diseñar y mantener un esquema.
- Los cambios estructurales necesitan migraciones controladas.

## 3. Decisión

Se propone utilizar **PostgreSQL** como sistema de gestión de base de datos relacional.

PostgreSQL almacenará los registros principales de:

- Usuarios y asignaciones de roles.
- Casos académicos.
- Clasificaciones y referencias.
- Asignaciones y reasignaciones.
- Actividades de seguimiento.
- Recomendaciones y notas.
- Historial y eventos de auditoría.
- Configuraciones de políticas, cuando corresponda.

Las operaciones relacionadas que deban mantenerse consistentes se ejecutarán mediante transacciones.

La persistencia será accesible desde el backend a través de una capa definida de acceso a datos; la aplicación web no accederá directamente a PostgreSQL.

## 4. Justificación

El modelo relacional resulta adecuado para representar los vínculos entre los casos y sus diferentes registros asociados.

El uso de transacciones permite coordinar operaciones como la resolución de un caso, la actualización de su responsable y la generación del historial correspondiente.

La capacidad de consulta relacional también facilita obtener información operacional sobre estados, categorías, responsables y actividades pendientes.

## 5. Consecuencias

**Positivas:**

- Integridad referencial.
- Soporte para transacciones.
- Consultas estructuradas.
- Persistencia duradera.
- Herramientas de migración y administración.

**Limitaciones:**

- Dependencia de una base de datos central.
- Necesidad de mantenimiento y respaldo.
- Posibles problemas de rendimiento si las consultas y los índices no se diseñan correctamente.
- Necesidad de controlar el acceso directo a las tablas desde los diferentes módulos.

## 6. Verificación

Se diseñarán pruebas para comprobar que:

1. Los follow-ups pertenezcan a casos existentes.
2. Las reasignaciones conserven los registros anteriores.
3. Una resolución inválida no modifique el estado persistido.
4. Una operación fallida no genere cambios parciales en las transacciones protegidas.
5. Los datos confirmados como persistidos sobrevivan al reinicio del backend.

**Pruebas relacionadas:** T-LIFE-01, T-LIFE-02, T-AUD-01 y T-REC-01.

## 7. Condiciones para reconsiderar la decisión

Se revisará esta estrategia si surgen nuevos requisitos que demanden otros patrones de almacenamiento o si mediciones verificadas muestran limitaciones que no puedan resolverse razonablemente mediante ajustes al modelo y las consultas.
