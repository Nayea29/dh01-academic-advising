# ADR-002 — Relational Database and Persistent Data Management

**Estado:** Seleccionada para el diseño propuesto  
**Fecha:** 9 de octubre de 2026  
**Responsable:** Pedro Peñate — Validation & Planning Lead  
**Equipo de arquitectura:**

**Escenarios relacionados:** QS-02, QS-03, QS-07

## 1. Contexto

El Academic Advising Case Management System necesita conservar información estructurada relacionada con estudiantes, asesores, solicitudes, asignaciones, actividades de seguimiento y eventos históricos.

Estas entidades mantienen relaciones que deben respetarse durante las operaciones del sistema. Por ejemplo, cada FollowUp debe pertenecer a un AdvisingCase existente y una reasignación debe actualizar la responsabilidad vigente sin perder los registros anteriores.

Asimismo, las transiciones de estado y sus eventos obligatorios de auditoría deben mantenerse consistentes, incluso cuando existan errores o modificaciones concurrentes.

La solución también necesita consultas estructuradas para supervisar casos, responsables y actividades pendientes, además de persistencia independiente del proceso backend.

Estas necesidades hacen necesario seleccionar un mecanismo de almacenamiento que permita administrar relaciones, integridad, transacciones y recuperación de información.

## 2. Alternativas consideradas

### Alternativa A — Base de datos documental

Una base de datos documental permite almacenar información flexible mediante documentos.

**Ventajas:**
- Flexibilidad de estructura.
- Adaptación a documentos con atributos variables.
- Posibilidad de agrupar información relacionada en una misma representación.

**Desventajas:**
- Mayor responsabilidad de diseño para mantener relaciones e invariantes entre registros.
- El modelo de casos, usuarios, asignaciones y seguimientos requiere asociaciones explícitas.
- Las consultas y actualizaciones que involucran múltiples entidades pueden necesitar coordinación adicional.

Una base documental puede ofrecer transacciones, pero su flexibilidad no proporciona una ventaja determinante para las relaciones identificadas en DH-01.

### Alternativa B — Base de datos relacional

Una base de datos relacional permite representar entidades relacionadas mediante tablas, claves y restricciones de integridad.

**Ventajas:**
- Soporte para relaciones estructuradas.
- Restricciones de integridad referencial.
- Operaciones transaccionales.
- Consultas estructuradas para reportes.
- Herramientas maduras de administración y respaldo.

**Desventajas:**
- Requiere diseñar y mantener un esquema.
- Los cambios estructurales necesitan migraciones controladas.
- El diseño de índices y consultas requiere atención para evitar problemas de rendimiento.

## 3. Decisión

Se selecciona **PostgreSQL** como sistema de gestión de base de datos relacional para DH-01.

PostgreSQL almacenará los registros principales de:

- Usuarios, roles y ámbitos de acceso.
- Estudiantes y programas académicos sintéticos.
- Casos académicos y sus clasificaciones.
- Asignaciones vigentes e históricas.
- Solicitudes de información adicional.
- Actividades de seguimiento.
- Recomendaciones y notas internas.
- Eventos de auditoría e historial.
- Sesiones técnicas de autenticación.
- Catálogos y configuraciones de políticas, cuando corresponda.

La persistencia se organizará mediante **CMP-09 — Persistence Layer**, utilizando repositorios y una unidad de trabajo transaccional para coordinar los cambios relacionados.

Las operaciones críticas deberán ejecutarse mediante transacciones compartidas, incluyendo la modificación del caso y la inserción de los eventos obligatorios de auditoría.

Se aplicarán restricciones de integridad referencial, unicidad y validación de datos según las invariantes definidas en el modelo lógico.

Para gestionar modificaciones concurrentes de un mismo caso se utilizarán mecanismos transaccionales de PostgreSQL, incluyendo bloqueo de la fila correspondiente y comprobación de la versión esperada cuando la operación lo requiera.

La aplicación web C-WEB no accederá directamente a PostgreSQL. Todas las operaciones del dominio pasarán por C-API y sus componentes autorizados.

### Persistencia de sesiones

Además de los datos académicos, PostgreSQL almacenará la tabla técnica `SESSION`, utilizada por el mecanismo de autenticación propuesto en ADR-004.

Esta tabla conservará referencias a usuarios, el resumen del token de sesión (`tokenDigest`), fechas de creación, actividad, expiración y revocación.

Las sesiones constituyen información técnica de autenticación y no reemplazan los registros de auditoría del proceso académico.

## 4. Justificación

El modelo relacional resulta adecuado para representar los vínculos entre casos, estudiantes, responsables y acciones de seguimiento.

Las claves foráneas y restricciones permiten prevenir determinadas inconsistencias estructurales, mientras que las transacciones facilitan coordinar operaciones que deben confirmarse o revertirse conjuntamente.

Por ejemplo, una reasignación no debe conservar simultáneamente dos responsables vigentes ni perder el historial de la responsabilidad anterior.

Del mismo modo, una resolución no debe confirmarse si existen seguimientos pendientes o solicitudes de información abiertas.

PostgreSQL proporciona los mecanismos necesarios para implementar estas reglas en colaboración con los servicios de dominio. Sin embargo, la selección del motor no sustituye las validaciones de negocio que corresponden a C-API.

La capacidad de consulta relacional también facilita obtener información operacional sobre estados, categorías, responsables y actividades pendientes.

La elección responde principalmente a los drivers AD-01, AD-03 y AD-04, relacionados con la integridad del ciclo de vida, la trazabilidad y la consistencia de los seguimientos y resoluciones.

## 5. Consecuencias

**Positivas:**

- Integridad referencial entre las entidades.
- Soporte para operaciones transaccionales.
- Posibilidad de implementar restricciones de unicidad.
- Mecanismos de concurrencia y bloqueo.
- Consultas estructuradas para reportes.
- Persistencia independiente del backend.
- Herramientas de migración, administración y respaldo.

**Limitaciones y compromisos:**

- Dependencia de una base de datos central.
- Necesidad de mantenimiento, migraciones y respaldos.
- Posibles problemas de rendimiento si las consultas y los índices no se diseñan adecuadamente.
- Necesidad de controlar el acceso a las tablas desde los diferentes módulos.
- Las restricciones de base de datos no sustituyen las reglas de autorización ni todas las validaciones de negocio.
- La recuperación después de pérdida de datos requiere procedimientos de respaldo y restauración, no solamente reiniciar el servicio.

## 6. Verificación

La decisión se evaluará mediante las siguientes pruebas:

| Prueba | Objetivo |
|---|---|
| T-DATA-01 | Comprobar integridad referencial, relaciones entre entidades y restricciones estructurales, incluida la asignación vigente única. |
| T-TRIAGE-01 | Verificar que la clasificación y asignación inicial respeten las relaciones y condiciones definidas. |
| T-LIFE-01 | Confirmar que una resolución inválida no modifique el estado persistido. |
| T-LIFE-02 | Comprobar que operaciones concurrentes sobre un caso preserven las reglas de resolución. |
| T-AUD-01 | Verificar que las reasignaciones y demás operaciones relevantes conserven historial coherente. |
| T-TXN-01 | Comprobar que un fallo en una operación obligatoria revierta los cambios de negocio y auditoría de la misma transacción. |
| T-REC-01 | Verificar que los datos confirmados persistan después del reinicio del backend, manteniendo PostgreSQL disponible. |
| T-REC-02 | Verificar que un respaldo pueda restaurarse y conservar las relaciones y registros esperados. |

Estas verificaciones deberán ejecutarse sobre una instancia real de PostgreSQL de prueba cuando se evalúen propiedades transaccionales, restricciones y concurrencia.

Los resultados observados y sus evidencias se registrarán en los documentos de validación.

## 7. Condiciones para reconsiderar la decisión

La estrategia de persistencia podrá revisarse si:

- Surgen requisitos que demanden patrones de almacenamiento no cubiertos adecuadamente por el modelo seleccionado.
- Las mediciones de rendimiento evidencian limitaciones que no puedan resolverse razonablemente mediante índices, consultas o ajustes del esquema.
- Se establecen requisitos institucionales de disponibilidad o recuperación que exijan modificar la topología de datos.
- Aparecen nuevas integraciones o responsabilidades de almacenamiento que justifiquen separar determinados tipos de información.

Cualquier modificación deberá documentarse mediante una nueva decisión o revisión vinculada, conservando las razones y consecuencias de la selección original.
