# ADR-001 — Modular Monolith Architecture

**Estado:** Seleccionada para el diseño propuesto  
**Fecha:** 9 de octubre de 2026  
**Responsable:** Sergio Pérez — Software Architecture Lead  
**Equipo de arquitectura:**

- Sergio Pérez — Software Architecture Lead

**Architecture Drivers:** AD-01, AD-05, AD-07  
**Escenarios relacionados:** QS-02, QS-05, QS-07

## 1. Contexto

El Academic Advising Case Management System debe gestionar solicitudes de asesoría académica mediante un proceso centralizado que incluya creación, clasificación, asignación, seguimiento, reasignación y resolución de casos.

El sistema debe garantizar consistencia entre las operaciones del ciclo de vida, proteger información sensible y conservar registros históricos.

Horizon University dispone de recursos técnicos limitados y requiere una solución mantenible, independiente de otros proyectos y viable dentro del período de desarrollo establecido.

Estas condiciones hacen necesario seleccionar una arquitectura que permita organizar claramente las responsabilidades sin introducir una complejidad operacional innecesaria.

## 2. Alternativas consideradas

### Alternativa A — Monolito tradicional sin separación modular explícita

Consiste en desarrollar la aplicación backend como una única unidad sin límites claramente definidos entre las responsabilidades de negocio.

**Ventajas:**
- Menor esfuerzo inicial de organización.
- Un único proceso de ejecución.
- Despliegue relativamente sencillo.

**Desventajas:**
- Mayor riesgo de acoplamiento entre funcionalidades.
- Dificultad para modificar reglas sin afectar otras áreas.
- Menor claridad sobre las responsabilidades de cada parte del sistema.

### Alternativa B — Monolito modular

Consiste en desarrollar una aplicación backend unificada, organizada internamente en módulos con responsabilidades y contratos definidos.

**Ventajas:**
- Separación lógica de responsabilidades.
- Operaciones transaccionales dentro de una misma aplicación.
- Menor complejidad operacional que una arquitectura distribuida.
- Facilidad para realizar pruebas de integración.
- Posibilidad de evolucionar o extraer módulos en el futuro si existe una necesidad justificada.

**Desventajas:**
- Los módulos comparten el ciclo de despliegue de C-API.
- El crecimiento desorganizado puede generar acoplamiento.
- Es necesario mantener reglas de dependencia entre los módulos.

### Alternativa C — Arquitectura de microservicios

Consiste en dividir el sistema en servicios independientes que se comunican mediante mecanismos de red.

**Ventajas:**
- Despliegue independiente de servicios.
- Escalamiento diferenciado.
- Separación de responsabilidades a nivel de ejecución.

**Desventajas:**
- Mayor complejidad de infraestructura.
- Necesidad de gestionar comunicaciones distribuidas.
- Mayor dificultad para garantizar consistencia entre operaciones.
- Incremento del esfuerzo de monitoreo, pruebas y mantenimiento.

## 3. Decisión

Se selecciona como propuesta una arquitectura de **monolito modular**.

La solución estará compuesta principalmente por:

- **C-WEB:** aplicación web React para la interacción con los usuarios.
- **C-API:** backend Node.js/Express que concentrará las reglas de negocio.
- **C-DB:** base de datos PostgreSQL para almacenamiento persistente.
- **X-SIS:** servicio HTTP mock independiente que simulará la integración con el sistema académico institucional.

El backend se organizará mediante componentes lógicos con responsabilidades definidas:

- API Controllers.
- Authentication & Authorization.
- Case Management.
- Triage & Assignment.
- Follow-up & Resolution.
- Notes & Confidentiality.
- Reporting & Queries.
- Audit & History.
- Persistence Layer.
- SIS Integration Adapter.

Estos componentes corresponden a CMP-01 hasta CMP-10, documentados en la vista de componentes.

Los módulos colaborarán mediante contratos internos y utilizarán mecanismos de persistencia coordinados.

La separación modular no implica que cada módulo sea un microservicio ni que cuente con un proceso de despliegue independiente.

## 4. Justificación

El monolito modular proporciona un equilibrio entre la separación de responsabilidades y la simplicidad operacional.

Permite que las operaciones relacionadas con casos, asignaciones, seguimientos e historial se coordinen dentro de una misma aplicación, facilitando el uso de transacciones para mantener consistencia.

La arquitectura también permite organizar las reglas de negocio y reducir el impacto de modificaciones sobre componentes independientes.

No se identifica actualmente una necesidad confirmada de escalamiento o despliegue independiente que justifique asumir la complejidad de una arquitectura de microservicios.

La decisión responde principalmente a los drivers AD-01, AD-05 y AD-07, relacionados con la integridad del ciclo de vida, la mantenibilidad y la viabilidad del despliegue.

## 5. Consecuencias

**Positivas:**

- Menor complejidad de despliegue.
- Integración directa de módulos relacionados.
- Facilita la consistencia de las operaciones de negocio.
- Organización clara de responsabilidades.
- Mantenimiento compatible con un equipo reducido.
- Posibilidad de comprobar reglas críticas mediante pruebas de integración.

**Limitaciones y compromisos:**

- Los módulos comparten el ciclo de despliegue de C-API y no se despliegan independientemente en la arquitectura seleccionada.
- Una falla crítica del proceso backend puede afectar múltiples funcionalidades.
- Los límites internos deben respetarse mediante convenciones, revisiones y pruebas.
- El uso de una base de datos compartida requiere controlar las operaciones realizadas por cada módulo.
- Un crecimiento significativo de carga o de equipos podría requerir reconsiderar la arquitectura.

## 6. Verificación

La decisión arquitectónica se evaluará mediante las siguientes pruebas:

| Prueba | Objetivo |
|---|---|
| T-MOD-01 | Comprobar la separación de responsabilidades, dirección de dependencias y capacidad de realizar cambios controlados. |
| T-LIFE-01 | Verificar que las reglas del ciclo de vida se mantengan durante la colaboración de los módulos. |
| T-TXN-01 | Comprobar que las operaciones críticas preserven su consistencia transaccional. |
| T-DEP-01 | Verificar el despliegue reproducible de C-API y sus dependencias. |
| T-REC-01 | Comprobar la recuperación del backend después de un reinicio, conservando los datos persistidos. |

Estas verificaciones permitirán evaluar los efectos y limitaciones de la arquitectura seleccionada.

Los procedimientos, criterios y resultados se gestionan en los documentos de validación.

## 7. Condiciones para reconsiderar la decisión

La arquitectura podrá revisarse si aparecen necesidades demostradas de:

- Escalamiento independiente de capacidades específicas.
- Despliegue autónomo de determinados módulos.
- Mayor aislamiento de fallos.
- Separación de responsabilidades entre múltiples equipos de desarrollo.
- Cambios institucionales que hagan insuficiente el modelo operacional seleccionado.

Cualquier modificación deberá documentarse mediante un ADR nuevo o una revisión vinculada, conservando la justificación histórica de la decisión.
